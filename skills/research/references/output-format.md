# Research Document Format

Use this structure for the output document. Skip sections that don't apply — never pad with filler.

```markdown
# Research: <Topic>

> One-paragraph executive summary: what this is, how it works, and the key takeaway.

## Architecture

Mermaid diagram showing the major components and how they connect. Keep it to the level of detail that fits on one screen.

\`\`\`mermaid
graph TD
  A[Component] --> B[Component]
\`\`\`

Brief explanation of the architecture — design decisions, trade-offs, constraints.

## Key Components

| Component | Location | Responsibility |
|-----------|----------|----------------|
| Name | `path/to/file.ts:42` | What it does |

## Data Flow

Step-by-step trace of how data moves through the system for the primary use case. Reference specific files and functions.

1. **Entry point** — `path/to/handler.ts:10` — receives request / event / input
2. **Processing** — `path/to/service.ts:55` — transforms, validates, enriches
3. **Storage** — `path/to/repo.ts:30` — persists to database / external system

Include a sequence diagram if the flow involves multiple actors:

\`\`\`mermaid
sequenceDiagram
  participant A
  participant B
  A->>B: request
  B-->>A: response
\`\`\`

## Glossary

| Term | Meaning | Where used |
|------|---------|------------|
| DomainTerm | What it means in this codebase | `path/to/file.ts` |

## Dependencies

### Internal
- `module-name` — what it provides to this feature

### External
- `package-name@version` — why it's used

## Findings

### How it works
Narrative explanation of the mechanism. Prioritize non-obvious behavior, implicit contracts, and things a new developer would get wrong.

### Risks & Tech Debt
Concrete issues found during investigation. Each with file reference and severity.

### Open Questions
Things that couldn't be determined from the code alone and need human input.

---
*Generated by `/research` — <date>*
```

## Guidelines

- **Be specific**: `UserService.findById (user.service.ts:47)` not "the user service"
- **Be honest**: if something is unclear, say so in Open Questions
- **Be useful**: every section should help someone make a decision or avoid a mistake
- **No filler**: "This section covers..." preambles add nothing — cut them
- **Diagrams over prose**: a Mermaid diagram replaces paragraphs of explanation

Runbook for one orchestrator session. It owns the environments, the data, the dashboard and the final report; Sonnet worker agents execute scenario families and report JSON. Nothing here assumes the orchestrator has seen the code: every fact needed is in `references/`.

**Usage:** `/cloud-e2e run "<run name>" --group utr --solo --agents 2 --families R,O,M,W,P,C,L,MO,X [--compare <second env>] [--worker-model opus]`

## Scope boundary

The E2E verifies **one given on-prem bundle** against its oracles (api-pp journal, PEP, expected values): every verdict is PASS/FAIL/BLOCKED for that environment alone. Running a second environment and diffing (the `diff` field) is an optional overlay (`--compare <second env>`); it is never the basis of a verdict. Worker model: Sonnet (`model: "sonnet"`) for regular runs; `--worker-model opus` only for validation runs whose workers still judge the scenarios themselves (the first run, 2026-10-14, was one).

## Hard rules

- Never leave a past on-call day with an odd number of active stamps (24 h phantom Einsatz on-prem, PPCLOUD-14167). Every worker counts before stopping; the orchestrator re-checks `created_data` at the end.
- One agent per employee at a time. Families map to employees (table below); never launch two families that share an employee concurrently.
- Tenant configuration (feature flags, PEP rights, closing dates, version override) changes only in Phase 0 and in the exclusive phases (P, C part 2), by the orchestrator or the configuration-owning worker, never by another worker.
- Credentials (RDP passwords, service secrets, user passwords, SYS connect strings) live in local credential files or the operator's own terminal; they never appear in briefs, notes, dashboard rows, the report artifact or chat.
- Workers run through the Agent tool with `model: "sonnet"` (`--worker-model opus` only for validation runs); the orchestrator never executes scenarios itself except gates and the X family.
- PEP is one RDP session per box: workers hold the db lock `locks/<tenant-id>~pep` of the run dashboard (core `references/coordination.md` §3.2; `{{PEP_LOCK_DOC}}` / `{{PEP_LOCK_STEPS}}` in the briefs) while driving PEP; prefer the DB oracle for reads. PEP definitions and paints (Phase 1, incl. E2's Pikett plannings) are the orchestrator's.
- **Fixture-day protection**: no family writes stamps on a planning whose window crosses midnight (Nacht, Pikett) when the next day carries fixture data (prepared read day, carve, Kombi, another family's data-fix day) or another scenario's stamps — on-prem re-interprets D+1 and silently drops what is not derivable from stamps (master-1822 lost the R-04 carve twice: W-01/W-07b and P-01b, N-W-3). The day map (Phase 2) applies it; a lost fixture is re-applied by the orchestrator (seed step q) and its readers re-run (RE).
- Identify fixture blocks and stamps by (employee, day, PA code, time window), never by id: every re-interpretation renumbers them (carve 402 → 442 → 482).
- Never use a production kubectl context or production data; every tenant of the run is a CT DeployMate environment.
- Report outcomes faithfully: BLOCKED is a verdict, not a failure; a mismatch between the environment under test and the `--compare` environment is recorded in `diff`, never as a verdict.
- Box-side DML (rights, closing dates, PSC enqueues, seed fixes) is the orchestrator's (or the configuration-owning P/C worker's) job and is logged in `results/<run>/created/*.jsonl`; workers report a needed change in `blockers` instead of running it.

Creating the test environment is part of the E2E, not a precondition. One environment for the bundle under test; `--compare <second bundle>` provisions a second one the same way.

1. **Day map and date shift.** The orchestrator writes `results/<run>/day-tokens.md` from the run date R (Europe/Zurich) before generating any prompt: absolute data days (P0..P3, `KOMBI_DAY`, `CARVE_DAY`, X-02/X-03 targets, Pikett plannings — they never move) and R-relative days (TODAY = R; write window R−7..R−1, oldest UI-writable day **R−6** while KD-3 is open; WD2 = the last weekday before R, WD1 = the weekday before WD2; WE1/WE2 = the weekend inside the window; P-03 day −1 / −2). It may override days per family and per employee (master-1822 had to: E1's only free past weekday; run a1801: W's E3 days), by these rules: never another family's fixture day; fixture-day protection (hard rule); the planning type the scenario needs (W-01/W-02/W-06/P-01b/MO-05 a day planning, not a night card; MO-02, O-06, W-10 need a planning on TODAY; W-05 a planning-less day; C-04 ≥ R−6). Prompts are generated with `python3 -I scripts/gen-prompts.py results/<run>/run-config.json --group utr --solo [--run-date R′]` (the one config file of the run: ids, logins, bundle, absolute data days, `roster_start` / `painted_days`, per-family and per-employee day overrides, `night_days` / `planless_days` / `carry_days` from `write-days.sql`, fixture days from `verify.sql` V4) and never patched by hand afterwards — a correction goes into the brief or the config and the prompts are regenerated. A per-employee override reaches the brief body through the role-tagged tokens (`{{E3_WD2}}` …), so no worker remaps dates. The generator refuses a day-rule violation (older than R−6, a fixture day, a night before a fixture day, a wrong planning type, a prepared day equal to a write token or before the roster start without being painted, P3 < R−6), a scenario id handed to two families, and an override no brief line uses; `--allow-violations` prints them into the prompt header instead. Family C yields `C-part1.md` and `C-part2.md`.
When the run continues on a later day R′ (a family launched after midnight, a second session day): before launching anything on R′ (1) recompute the R-relative tokens with R′; (2) check every absolute write day of each pending family is still ≥ R′−6 and replace one that left the window by the rules above, or mark its scenarios BLOCKED "write day left the window" (WE1 = R−6 leaves it first); (3) P-03 uses day −1 / −2 of the day P runs, MO-02 / O-06 / W-10 need a planning on R′ (paint the Pikett for E2's new TODAY, step s), and the KD-7 day set (today / future) moves with R′; (4) daily pre-flight: `pe-ready.sh` (PEP session expiry; cold start if PEP is down), one harness read per login in use, DeployMate gate G0 (auto-stop off; `refresh-ip` after an IP change); (5) add "Day map v2 (R′)" to `env-facts.md` and regenerate the pending prompts (`gen-prompts.py --run-date R′`). Workers that cross midnight follow the agent-brief rule "Date shift".

Scheduling rule: R reads P0..P3 only, so it may run while W writes WD1/WD2 of the same employees; M reads whole-month totals (run it after W on E1, or note the W writes); everything else sharing an employee is sequential. O must finish before P (P-04) and C part 2 (C-05/C-07a reuse E2's Pikett). Suggested order with N workers: X (orchestrator, incl. G4b/X-05) → launch R, O, W, MO up to N → then M, L, C part 1 as slots free → P alone → C part 2 alone → RE if an environment fix happened during the run.

3. On the worker's JSON report: validate the schema; a scenario whose `findings_confirmed` holds a `KD-n`, or an id that scenarios.md "Bundle-aware expectations" lists for that scenario and the run's bundle class (F-n, D-n, N-X-1, N-D-4 …) with a matching signature, is a KNOWN-FAIL — write `envM: "fail"` and start the dashboard `verdict` with `KNOWN-FAIL <id> <ticket>`, never into `new-findings.md`; a FAIL whose signature differs from the listed one is new; W-07b goes into the W-07 row; a `PENDING` verdict (C part 1 only) keeps `envM: "pending"` with `verdict` "part 1: <observed>; part 2 pending"; for each scenario write the dashboard row: `envM` ← `verdict` of the environment under test, `envP` ← `compare.verdict` (only in a `--compare` run; the default single-version dashboard has no compare field, so leave `envP` out), `verdict` (one line: finding ids confirmed + key numbers + `diff`), `evidence` (folder path), `notes`, `agent`, `updated`; append `new_findings` to `results/<run>/new-findings.md`; append `created_data` to `results/<run>/created-data.json`; act on `blockers` (G4b refresh, a missing Pikett planning, log lines the worker could not read, DML a classifier refused). **Screenshots:** a FAIL / KNOWN-FAIL / BLOCKED-by-error scenario without `shots` goes back to the worker (SendMessage: "add the issue screenshot") before its row is final; open each PNG once — a welcome tour, a spinner or an unframed page goes back too. ## Phase 3 — Consolidation

1. Findings table: for each finding id from the report artifact (F1–F14, D1–D4): `confirmed` / `not reproduced` / `partially` / `not testable`, with the scenario ids and the numbers (environment under test vs PEP, plus the compare environment when run). Known product defects KD-1..KD-7, D3 and the 1801-bundle defects get their own block (KNOWN-FAIL / now passing = fixed → update the status column of the KD table in `references/scenarios.md`). New findings get the next ids (N1, N2, …) with evidence paths.
2. Scenario matrix: export the dashboard rows (`ArtifactData list collection=scenarios`) to `results/<run>/matrix.json` and render the pass/fail counts per family and env.
3. Update the report artifact (the investigation artifact the user names; read it first with `Artifact read`, keep every other section unchanged) in its "E2E results" section: run metadata (date, env ids, bundle versions, cloud build, flags), the findings table, the matrix, the dashboard link, the fixtures folder, decisions needed from NEON, cleanup status. Republish to the same URL. Every FAIL / KNOWN-FAIL row of the matrix and every confirmed finding card shows its issue screenshot(s): publish the PNG files with the report through `files` (published path `shots/<scenario-id>-<n>.png`) and reference them as `<img>` thumbnails with the worker caption, linking to the full-size file.
4. Fixtures as contract evidence: keep `results/<run>/fixtures/` (every environment of the run, all employees, the seeded window) and the diff outputs; they are the regression baseline for the next run.
5. Cleanup per `references/gates.md` §6; set `run/meta.status` to `done`; write the summary to the user: confirmed findings, new findings, blocked scenarios and why, link to the artifact and the dashboard.

## Worker reporting contract (summary; the schema is in assets/agent-brief.md)

`{family, agent, tenant, scenarios:[{id, verdict, observed, expected, oracle, evidence[], shots[], findings_confirmed[], new_findings[], compare:{tenant, verdict, observed, evidence[]}|null, diff, notes}], created_data:[{env, employee, date, kind, id, cleaned}], blockers:[]}` (+ `restored[]` from P, `conclusion` from RE) — verdicts `PASS | FAIL | BLOCKED` (`PENDING` only in C part 1); evidence paths relative to the results folder.

# Data plan — audit the seed, then create what is missing

Executable runbook: [`groups/utr/scripts/seed/README.md`](../scripts/seed/README.md) (Phase 1 steps a–i, plus steps j–r for the data gaps root-caused on 2026-10-15; SQL, flows, expected numbers, execution order). This file keeps the target model and what the DeployMate `customer-roster` seed actually provides. With `--compare`, the second environment gets the identical recipe.

Goal: a deterministic data set that exercises every scenario in scenarios.md, created by script so it can be replayed on any fresh DeployMate env and eventually baked into a dedicated "UTR dump" image.

## 1. Month layout (relative to the run date)

| Window                | Purpose                                                                                                | Locking                                                                                                                   |

| M-1 (previous month)  | prepared READ data (R, O, M, X families) — never written during the run                                | open                                                                                                                      |
| M0 (current month)    | WRITE scenarios (W, O-04/O-05, MO, C-03..C-05), days ≤ today; past-days window 7 → use the last 5 days | open                                                                                                                      |

**Reality on a DeployMate `customer-roster` seed (first run 2026-10-14):** the seed plans only a 14-day window around the seed date (`manifest.roster`, weekdays, seed date −7..+6); M-1 and M-2 are empty and there is no history to close. The prepared READ days therefore live in the first four roster weekdays (P0..P3, P0 older than the 7-day write window), the write days are the last two past weekdays, and M-2 closing scenarios (P-02, W-08) need a closing date set inside the roster window or stay BLOCKED. Day rules: `groups/utr/scripts/seed/README.md` § Dates.

## 7. Creation recipes

Commands, coordinates and order: `groups/utr/scripts/seed/README.md` (steps c–e, § PEP coordinates). Building blocks:

- Stamps: pep-driver flow `create_stamp zeit=HH:MM [datum=dd.mm.yyyy]` (next-day out-stamp via `datum`), persisted with `stampeditor_commit` (confirms the "Trotzdem planen" rule popup).
- Manual Zeitsumme / Fixer Saldo: `add_zeitsumme dauer=H:MM pa_code=-1|-9 [gutschrift=GLAZ]`.
- Ad-hoc block: `add_block beginn=HH:MM ende=HH:MM pa_code=57 [kommentar=…]` (presence codes are rejected).
- Seed-ZEITSUMME fix: `groups/utr/scripts/pep/pe-del-zs.sh` + `stampeditor_commit`; re-interpretation `groups/utr/scripts/pep/pe-reinterp.sh`.
- Paint / overpaint a Dienst: palette radio "Ganz" + icon + `drag_paint` (repeat once if the first drag does nothing). api-pp direct planning no-ops on days with stamps, so paint before stamping.
- Definitions and palette: PEP Definitionen → Dienst (manual pep-verify driving; no flow yet).
- Rights: SQL on the planner role (`scripts/seed/common/rights.sql`), not UsrAdmin.
- Users: none to create — the seed's `dmseed-<kuerzel>` logins exist in Keycloak and POLYUSER.
- Closing date (exclusive phases only): Datei → Abschlussdatum festlegen, or `SYSTEM_KATEGORIE_VARIABELN.ML_/SL_ABSCHLUSS_DATUM` of the category node.
  The flows live in `groups/utr/scripts/seed/flows/` (copies of the live-verified pep-driver flows; push with `scripts/pep.sh <id> push-seed-flows`, contribute upstream).
  After creation capture the G5 fixtures (README step g) and compare the prepared days with the table in §4.

## 8. Packaging of the seed (inside the skill, no DeployMate preset)

The skill seeds the environment itself as Phase 1 of every run: a replayable recipe = SQL files executed through the box's sqlplus (definitions, employee settings, rights, closing date, plannings) + pep-driver flows with parameters (stamps, blocks, carved absence, Zeitsumme, Fixer Saldo — anything P2 must interpret) + myPP writes where the product path is the right one. Every created object is logged (`results/<run>/created/*.jsonl`) and verified against PEP's Stempeleditor numbers before the scenarios start. The recipe lives under the skill's `scripts/seed/` and is replayed, not re-invented, on the next environment.

A DeployMate seed preset (`utr-time-recording`) was studied and rejected as too much effort (16–20 dev days; spec kept in `references/deploymate-seed-preset.md` for reference). An Oracle dump is not a substitute either (dates frozen, seed skipped, re-seed refused on dump envs).

Lessons from the first run (details and workarounds: `groups/utr/scripts/seed/README.md` § Known seed defects): the `customer-roster` layer writes static planned ZEITSUMME rows that double-count once a day is stamped (re-run PEP's stamp interpretation for every seeded day); the offline manifest's logins drift from the live DB seed (take logins from POLYUSER, `dmseed-<kuerzel>`); PolyID breaks usernames with umlauts (prefer ASCII kürzel); mobile-app rights = POLYUSRROLE_DETAIL rows on the seed planner role + `IFDBA.ENQUEUE_PERSISTENCE_STATE_CHANGE('PERMISSION_ROLE', <role>, null, null, 2471, null)` (operation ids 1 READ, 2 MODIFY, 3 DELETE, 4 CREATE, 5 PRINT, 6 EXECUTE); PolyID's brute-force detection locks an IP per provider without expiry — never probe logins with guessed usernames.

# Cloud E2E — multi-group, multi-person regression on DeployMate envs

Runbook for the **env steward** and the **group runners** of one run. Workers are Sonnet subagents that execute one family of one group and report JSON; runners and the steward never execute scenarios themselves (except gates and runner-owned families such as UTR X). Every fact a session needs is in `references/` and in the group package `groups/<key>/`.

## Roles

| Role             | Who                                               | Owns                                                                                                                                                                                                                                                                     |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Env steward**  | one person per run (recommended: also runs `utr`) | every DeployMate env of the run (owner-only calls: create, DM-213 repair, auto-stop, SSH keys, shares, LEGACY / UNIFIED, reseed, destroy), the common seed (kits, flag baselines, stage objects), the run dashboard, HARD / STAGE windows, PolyID unlocks, consolidation |
| **Group runner** | one Claude Code session per person and group      | its claims (actors, nodes, logins, pools, prefixes), its group seed, its workers, its rows and findings, its windows' restores                                                                                                                                           |
| **Human tester** | 2–3 people for the `manual` group                 | the manual checklists (phone, Teams, PEP-RDP, mail, Staging, smartPEP, externals)                                                                                                                                                                                        |

## Commands

| Command                                                                                                      | Who                 | Does                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------ | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `steward up <run> --envs X,Y [--pin PP_SERVICES=0.0.N \| --pr <id>] [--groups <keys>]`                       | steward             | S0–S2 (`references/steward.md`)                                                                                                                       |
| `steward add-runner <run> --name <n> --sub <polyid sub> --ssh-pub <file> --env X [--level OPERATOR\|VIEWER]` | steward             | DeployMate share, SSH key append (≤ 5 per env), `runners/<n>` placeholder in `envs/<id>`; then asks the steward to share the dashboard at Contributor |
| `run <run> --group <key> [--agents N] [--families …] [--worker-model opus] [--run-date YYYY-MM-DD]`          | runner              | R0–R5 on the env the registry assigns (`envs/<id>.partitions`)                                                                                        |
| `run <run> --group <key> --solo`                                                                             | one person          | own env through the steward path, then R0–R5 in the same session (no shares)                                                                          |
| `window <run> --env X --id <window-id> request\|release`                                                     | runner / steward    | the window protocol (`references/coordination.md` §4)                                                                                                 |
| `status <run>`                                                                                               | anyone              | registry, claims, locks, windows, progress per group (db reads only)                                                                                  |
| `manual <run> --session teams\|phone\|pep-rdp\|mail\|staging\|smartpep\|externals`                           | runner with testers | prints the session checklist from `groups/manual/`; the tester's results become rows                                                                  |
| `steward consolidate <run>`                                                                                  | steward             | S5: export, matrices, report artifact, cleanup check; destroy only on the user's word                                                                 |
| `/utr-e2e "<run>" [--agents N] [--families …] [--compare <env>] [--worker-model opus]`                       | one person          | = `run <run> --group utr --solo`: today's UTR behaviour, `--compare` unchanged, results in `results/<run>/`                                           |

## Files

- `references/` — `coordination.md` (db schema, claim / lock / window protocols, heartbeats, stale takeover, F1 / F2 fallbacks); `steward.md` (provision, DM-213, partition, kits, flag baselines, stage objects, pre-flight, consolidation, teardown); `env-plan.md` (the 2-env model, window classes and ids, conflict register, seed partition, schedule); `env-setup.md` (topology, capability mechanism, DeployMate facts, gates G0 / G1 / G3, api-pp / api-gw access, myPP access); `harness.md` (CLI contracts of every helper, redaction, host guards); `lessons.md`, `troubleshooting.md` (generic; groups add their own).
- `assets/` — `agent-brief.md` (generic worker brief + `{{GROUP_BRIEF}}` slot + PEP-lock protocol + report schema); `recheck-brief.md` (re-check after an environment fix); `dashboard.html` (run dashboard, multi-group, read-only page); `dashboard-compare.html` (UTR `--compare` runs).
- `scripts/` — `gen-prompts.py` (prompt engine: `--group`, `--solo`, `--claims`, `--dry-run`, `--check-catalogue`); `dm-join.sh` (runner join: own reveals, test-data, `/32` union, PEP inventory, probes); `psc-enqueue.sh` (gate G4b events); `flags-baseline.py` (per-env flag baseline, contradictions, G-FLAGS compare); `sql.sh` + `dm-sql.ps1`, `tunnels.sh`, `pep.sh`, `diff-fixtures.py`; `pp-plan.sh`, `plan-day.sh`, `api-pp.sh`; `pep/pe-ready.sh`, `pep/pe-paint.sh`; `seed/common/` (steward kits); `harness/` (browser and ops helpers, `references/harness.md`).
- `groups/<key>/` — one package per group (`group.json`, `rules.json`, `references/`, `assets/`, `seed/`, `scripts/`): `utr`, `swap`, `booking`, `planner`, `hp`, `ts`, `partner`, `auth`, `ops`, `shared`, `manual`. UTR's own runbook is `groups/utr/references/runbook.md`.

DeployMate is driven through the `deploymate` skill (`dm-login-capture.mjs`, `dm-api.sh`), PEP through `pep-verify`.

## Phases

| Phase | Steward                                                                                                                                                                                                                                                                                  | Group runner                                                                                                                                                                                                                               |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0     | **S0 provision** per env: `dm-api.sh create` (same pin on every env, one wave of ≤ 2), wait, auto-stop off, DM-213 repair (operator SYS step in the steward's own terminal), services / tenant health, own reveals, tunnels, PEP cold start, `sql.sh --install`                          | **R0 join**: DeployMate login once per machine; send `userId` (`dm-api.sh me`) and the SSH **public** key to the steward; wait for the env share and the dashboard share (Contributor); `scripts/dm-join.sh <env>`; write `runners/<name>` |
| 0b    | **S0b gates + registry**: G0, G1 (version, capabilities, bundle class), partition (`envs/<id>.partitions` from every `group.json`; logins from `POLYUSER.KUERZEL`, ASCII only, before any login), publish the dashboard, seed the rows of all planned groups, `envs/*`, `schedule/<env>` | **R1 claim**: create `groups/<key>` (no `if_version`); one batch of claim creates inside the partition; export `claims.json`                                                                                                               |
| 1     | **S1 common seed** per env (`references/env-plan.md` §6.2): audit, rights, R0 rows + STAMM fix, definitions kit, role kit, one G4b batch, gates G4b / G-ROLES, flag baseline + G-FLAGS, stage objects on DM-X with the user's OK; every step logged in `kits/<env>`                      | **R2 group seed**: `groups/<key>/seed/*` on its own claimed rows; membership moves into kit groups + enqueue; PEP steps under `locks/<env>~pep`; the group gates                                                                           |
| 2     | **S2 operate**: daily pre-flight per env (G0, auto-stop, services, PEP up, allowlist union, GLN after 00:00); PolyID unlocks; owner-only calls on request; grants HARD windows; S-CT-\* announcements                                                                                    | **R3 fan-out**: `gen-prompts.py … --group <key> --claims claims.json`; Sonnet workers within the pace rule; window check before every launch; report validation; KNOWN-FAIL mapping; issue-shot upload; row writes; heartbeat ≤ 10 min     |
| 3     | **S5 consolidate**: export rows, summaries, findings; per-group / per-env matrix; one report artifact; cleanup check; TTL decision on the user's word                                                                                                                                    | **R4 report + R5 release**: cleanup from `created_data`; `groups/<key>.summary`; release claims and locks; group `done`                                                                                                                    |

The steward is a role, not necessarily a separate person: in the recommended plan (`references/env-plan.md` §7) the steward also runs `utr`.

## Group runner — the loop in detail

1. **R0.** `scripts/dm-join.sh <env>` must print `ssh … ok` and `db ok` (and `pep agent ok` for PEP groups with `--probe-pep`). Write `runners/<name>` with ArtifactData (`set`, no `if_version`; later `update` with `if_version`): `{machine, groups, envs, activeWorkers: {}, heartbeat}`. Personal ops sessions (portal ops, PolyID ops) are headed logins into a profile outside `results/`, right before the families that need them (≈ 1.5 h validity).
2. **R1.** Read `envs/<env>.partitions` and the group's `group.json` roles / partition; pick the actors by the group's `references/data-plan.md`; create `groups/<key>` and one `batch` of `claims/<env>~<kind>-<id>` creates (`coordination.md` §3). A refused create = partition conflict: delete what this batch created, stop, tell the steward. Export the claims (`ArtifactData list collection=claims`, filter by your group) to `results/<run>/<group>/claims.json`.
3. **R2.** Follow `groups/<key>/seed/` and `references/data-plan.md`; DML only on claimed rows; G4b events with `scripts/psc-enqueue.sh`; paints with `scripts/pp-plan.sh` (PEP `pe-paint.sh` only under the lock); run the group gates and record them in `results/<run>/<group>/env-facts.md`.
4. **R3.** Write `results/<run>/<group>/run-config.json` (ids, logins, days, `env_role`, `runner`, `dashboard_url`, `coordination`; never credentials) and generate the prompts: `python3 -I scripts/gen-prompts.py results/<run>/<group>/run-config.json --group <key> --claims results/<run>/<group>/claims.json`. Never patch a prompt: change the config or the brief and regenerate. Launch each worker with the Agent tool, `subagent_type: "general-purpose"`, `model: "sonnet"` (`"opus"` only with `--worker-model opus`), description `<GROUP> E2E family <F>`.
   - **Before every launch** read `windows/` of your env: a `draining` or `active` window that pauses `<group>:<family>` (or any HARD window, or a LOGIN window for a login-first family) → do not launch. Keep `runners/<name>.activeWorkers` current (`{env: {"group:family": n}}`) on every launch and hand-back.
   - **Pace rule**: N = 2 by default; ≤ 3 for groups with ≥ 3 disjoint lanes (swap, booking, partner, ops); the group's `assets/schedule.md` gives lanes and order. The moment a worker hands back, launch the next schedulable family in the same turn, then do the bookkeeping.
   - **On a report**: validate the schema; map KNOWN-FAILs by the signatures of the group's `known_deviations` file (`group.json`; usually `references/known-deviations.md`) — `verdict` starts with `KNOWN-FAIL <id> <ticket>`; number new findings `N-<GROUP>-<n>` and create `findings/<group>~<id>`; a FAIL / KNOWN-FAIL / BLOCKED-by-error row without `shots` goes back to the worker (SendMessage) before it is final — open each PNG once; upload shots to the dashboard asset store (Artifact tool, `url` = dashboard, `asset: true`, `file_paths` ≤ 25) and write `shots: [{id, url, caption, kind}]` with the returned `url`; write the row `scenarios/<group>~<id>` with `if_version` (`status`, `verdict`, `evidence`, `notes`, `agent`, `runner`, `env`, `updated`); append `created_data`; act on `blockers` (G4b refresh, DML a classifier refused: run it yourself only if it is on your own claimed rows, else ask the steward).
   - **Heartbeat**: `runners/<name>.heartbeat` at least every 10 min while the group runs.
5. **R4 / R5.** Cleanup from `created_data` (verify through the oracle), `groups/<key>` gets `summary` (counts by verdict, blocked reasons, cleanup state, open created data) and `status: done`; delete your claims and any lock you still hold (pinned deletes); set `activeWorkers` to `{}`.

Re-checks: when an environment fix (G4b refresh, PolyID unlock, service repair) invalidates earlier BLOCKED / FAIL verdicts, launch one worker from `assets/recheck-brief.md` (UTR: `groups/utr/assets/family-briefs/RE.md`) with the affected scenarios; its verdicts replace the earlier ones (`notes: previous: …`).

## Solo mode

`run <run> --group <key> --solo` (and `/utr-e2e`) = the steward path for one env and the runner path for one group in one session: no shares, results in `results/<run>/` (`gen-prompts.py --solo`), the dashboard still holds rows and the PEP lock (same code path; the owner writes everything). The group's `group.json` decides the env shape (`env.preferred`, pin, stage objects); the kits run only for that group's needs. Group `utr` in solo mode follows `groups/utr/references/runbook.md` end to end, unchanged (Phase 0 → 3, `--compare`, `dashboard-compare.html`).

## Coordination store

The run dashboard's artifact database is the store (`references/coordination.md`): `run/meta`, `envs/<env>`, `kits/<env>`, `stage/<object>`, `schedule/<env>` (steward, write `admin`); `runners/<name>`, `groups/<key>`, `claims/<env>~<kind>-<id>`, `locks/<env>~pep|jobs`, `locks/ct~gwmock`, `windows/<env>~<id>`, `scenarios/<group>~<id>`, `findings/<group>~<id>`, `manual/<session>` (runners). Claims, locks and windows are created **without** `if_version` (create-if-absent) and changed or deleted **with** it (compare-and-set). The page only reads. The mode is a run setting (`run/meta.coordination`, copied into every run config): `artifact-db` (default, after the two-person dry run passed), `gcs` (F1) or `degraded` (F2).

## Hard rules (also in every worker brief)

1. **Never production**: no production kube context, no `*.polypointservices.ch` host (every helper refuses it), no Staging (production cluster). Beekeeper on Staging is for humans only.
2. Never call `/test/**` on any host; never call GAT `clean` or `shift-trades`; never run a POMA job without `tenantIds=<own env>`; never run Tier B / D jobs; never restart the gateway mock or delete its inbox; never press a cache reset / clear, "Disable incompatible features", "reconcile enabled_for", "run automated fix" or key rotation.
3. Never edit the run partner. Every stage-wide change needs a `windows/ct~*` doc and the user's OK.
4. Messaging: owned recipients only; Send Messages only inside W-Y-MSG; tenant 2FA only inside W-Y-TENANT2FA; per-user TOTP override otherwise; ≤ 2 password submissions per login per harness call; every wrong password is followed by a success from the same IP; PolyID unlock = steward only.
5. One agent per employee at a time; only claimed actors and days; DML only on own claimed rows. Shared rows (kits, `DMSEED:Planner`, global PEP settings) are changed by the steward (or by UTR P / planner PSP-21 inside their windows).
6. PEP only under the db lock (one desktop per box, no human RDP while a pep-driver agent holds the lock); prefer `pp-plan.sh` and the DB / api-pp oracles for reads.
7. Credentials (`coordination.md` §6): no secret leaves its owner's machine — own reveals (`dm-join.sh`), personal ops logins, the api-pp service secret from the runner's own vault access into a local 0600 file; nothing in briefs, prompts, rows, the report, chat or files under `results/`. The DM-213 SYS login never reaches any Claude session.
8. Report faithfully: BLOCKED is a verdict; KNOWN-FAIL needs a matching signature; every FAIL / KNOWN-FAIL / BLOCKED-by-error row has an issue screenshot.
9. **On a classifier or permission block: stop that action and report it as a blocker. Never retry it renamed, wrapped or through another tool.**
10. Destroy, reseed and TTL decisions only on the user's explicit word; reseed never during a run (it renumbers every group's ids). No git writes by any session or worker.

## Lessons and troubleshooting

- Read `references/lessons.md` (and the group's own lessons, e.g. `groups/utr/references/lessons.md`) before the first seed step.
- `references/troubleshooting.md`: symptom → cause → fix (DM-213, PEP agent, `pe-ready` exits, `sql.sh` 124, PolyID lockout, refused claims, held locks, stuck windows, dashboard access).

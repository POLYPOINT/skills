# Troubleshooting

- `412` and empty day plans on one tenant → stored version below the endpoint minimum: gate G1 (version override), then re-run the family.
- `500 UNKOWN_ON_PREM_VERSION` → version unparsable (e.g. `ERROR_LOADING`): fix the stored version, wait ≤ 3 min (portal cache + poma reload).
- Unified reads `500` (or `/days` 200 with an error envelope) for a range → a ZEITANRECHNUNG row with CODEART 'S' in it: pre-1801 = N-X-1 (api-pp `TimeAccountEntryType.S`), 1801 = F2 (SHIFT_CONTROL decode, "no suitable HttpMessageConverter"); judge on the response body, mark the scenarios `blocked` with that id (X-02 is the only scenario that creates such a row).
- Unified `/days` 404 / month 500 naming `AllowanceProfileNotFoundException` → D3 (1801): a dangling or not-yet-cached allowance profile id; restore the BLOCK row (X-03) or enqueue `ALLOWANCE_PROFILE`.
- A carve / ad-hoc fixture disappeared and a day's block ids changed → a re-interpretation of that day (a stamp write on the night before, a replan, a bulk interpretation): N-W-3, re-apply seed step (q) and re-run its readers; tighten the day map.
- Harness lands on `/tabs/home/main` instead of the day view, or the first navigation logs "no response" → navigation retry (agent-brief); not a product result.
- `pe-ready.sh` exit 4 "COLD START NEEDED" (agent down or no `TfrmPEPMain` after a box restart) or "DEPLOY NEEDED" (no agent token: pep-driver never deployed on this box) → PEP cold start (Phase 0 step 4); exit 5 = two PEP login windows → close one (`pep.sh <id> click 'window*="Anmeldung"[1] > button="Close"'`), rerun; exit 3 = IDM login failed → stop, check the user, never retry blindly.
- `sql.sh` exit 124 "timed out" → the box or the tunnel hangs; check the effect of a DML before re-running it.
- DeployMate `time-recording LEGACY` answers HTTP 500 → retry up to 3 times, 1 min apart (C family, 2026-10-16: 3rd try 200); the UNIFIED restore needs up to ~6 min to reach `config/features`.
- Unified `/days` 404 or block writes 500 `LEGACY_TIME_RECORDING_OPERATION_FAILED` with an api-pp "Shift definition with id N not found" cause → gate G4b not done for N (Phase 1), not a product finding until it persists after the refresh.
- Classic day plan `500` → F3 (NPE on journal entries without shift type/account).
- Unified `/days` / month `500` on a Pikett day right after a stamp pair, api-pp NPE in `LegacyMyShiftsService.isOnCallBlock` → KD-4 (PA −1 block linked to the Pikett): remove the stamps (API or PEP), check the Pikett-Einsatz PA code (Phase 1 step n).
- Classic on-call add `409`, or any write on a planning-less day `500`, with api-pp on-call-event `400 "Failed to read request"` → KD-6, bundle below pp-services 0.0.1797 (Phase 0 version gate).
- Classic card shows only its title → `node.path` null → Phase 1 step (k) not done / not flushed (ORGANIZATION_STRUCTURE enqueue, hard reload).
- PEP agent not reachable → pep-verify preflight (fresh DeployMate boxes need `pep-auto-init.yml` and an active RDP session).
- P4 routes missing after DONE, api-pp exits on its Liquibase startup check → DM-213: deploymate skill §6a "DM-213 repair".
- **PolyID lockout (USER_OR_IP_LOCKED / logins fail after bad attempts)** → the orchestrator, on behalf of the operator running the E2E, uses `scripts/harness/polyid-unlock.mjs` (never a worker; it prints the target first). **Where the orchestrator may unlock itself:** CT (`--stage ct`, ct cluster) and Preview (`--stage preview`, demo cluster) — after asking the operator for the headed ops login. **Staging runs on the production cluster: never unlock there** — `--stage staging` makes no call and prints the manual steps; tell the operator which subject to remove in the Staging PolyID ops frontend and wait. Once per session (profile outside `results/`, e.g. `<scratchpad>/polyid-profile`): `node scripts/harness/polyid-unlock.mjs <profile> results/<run>/polyid <tenant-id> login` — headed, the operator signs in to the PolyID ops frontend with a support-ops/admin account. Then `… read` (headless: locked subjects of the tenant's provider with attempts / threshold / unlockAt, `applied-policies.json`) and `… unlock --subject my-ip` (this machine's public IP via `dm-api.sh my-ip`) or `--subject <the locked username from read>`; one exact subject only (no wildcards, never without `--subject` — the API would wipe the whole provider). Exit 0 = gone on re-read, 2 = subject not locked (nothing deleted, pick one from `read`), 3 = `LOGIN_NEEDED` → `login` with the operator, 4 = still present, 6 = 403 (account lacks admin rights). Provider id = `GET /api/admin/providers/<tenant-id>`; override with `--provider <id>`. Log the unlock in `run/meta.notes`, then re-run the blocked scenarios (RE worker).
- Dashboard shows "Live data unavailable" → the page was opened outside claude.ai or the viewer has no access; the data is intact (`ArtifactData list`).

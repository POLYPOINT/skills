# Scenario catalogue — myPOLYPOINT time recording, full feature

Conventions used by every scenario:

- **Environment**: every scenario runs on the environment under test (one on-prem bundle) and is judged against its oracles: PASS / FAIL / BLOCKED. With `--compare <second env>` the same steps run on the second environment afterwards and only fill `diff` (semantic difference), never the verdict. "ENV-M" / "ENV-P" below name the two bundles of the first run (master 0.0.1796 / PR 12910 branch build) where an expectation differs between them; since 2026-10-16 the per-scenario difference is stated per **bundle class** (next bullet and the table "Bundle-aware expectations").
- **Bundle class** (decides which known defects apply; the Phase 0 version gate writes it into `env-facts.md`, workers get it as `{{BUNDLE_CLASS}}`): **pre-1801** = every bundle without the PR 12910 roster refactor (APIPP-1801): the customer lines ≤ 26.3 (feature 26.3, main 26.0, 25.0 …) and pp-services master builds **< 0.0.1829** (e.g. 0.0.1822 of the master-1822 run); **1801** = pp-services master **≥ 0.0.1829** (first nightly with the merge, 2026-10-15), every feature line cut from it (26.4 by convention) and the PR 12910 branch builds `0.12910.N` (the first run's ENV-P, same model). The stored on-prem version (26.99.0 on every master-track box) cannot tell them apart; only the pinned pp-services version can.
- **Fixture identity**: a full re-interpretation (PEP replan, a PTC stamp write on the day or the night before, Neu interpretieren) gives the day's blocks new ids (master-1822: carve 402 → 442 → 482, main block 400 → 422 → 480). Identify fixture blocks and stamps by (employee, day, PA code, time window), never by block id; ids in examples are illustrations only.
- **Days and run date**: every day below is a token of the day map (`assets/agent-brief.md`): P0..P3 and the data-fix days (Kombi, carve, X-02/X-03 targets, Pikett plannings) are absolute and never move; TODAY, WD1/WD2, WE1/WE2, the write window and every "day −n" are relative to the run date R. A run that continues on a later day re-derives the relative tokens (SKILL.md "Day map and date shift"); "day −2" in a scenario means R−2 of the day the scenario actually runs.
- **Fixture-day protection** (every writing family): never write stamps on a planning whose window crosses midnight (Nacht 141, Pikett 150/151 windows) when the next day carries fixture data (a prepared read day, the carve, the Kombi, another family's data-fix day) or another scenario's stamps. On-prem (PolyTimeConnect / ECLINK) pairs a lone IN with the next morning's stamp and re-interprets D+1; a full re-interpretation rebuilds D+1's blocks from its stamps and silently drops whatever is not derivable from stamps (master-1822: W-01, W-07b and P-01b on E1's night before the carve day each destroyed the R-04 carve, N-W-3). PEP replans behave the same (W-06). Use a day planning or a night whose next day is free; if it happened anyway, the orchestrator re-applies the lost fixture (Phase 1 step q) and re-runs its readers (family RE).
- **UI**: myPP web through the skill's harness `scripts/harness/mypp.mjs` (Playwright, persistent profile per agent/env via `MYPP_PROFILES`; `mypp-inapp.mjs` for the in-app mobile path) — interactive `playwright-cli` only for exploration. Unified day view `/tabs/unified-time-recording?date=YYYY-MM-DD`, classic `/tabs/time-recording?date=YYYY-MM-DD`, month report child route `month-report?month=yyyy-MM`. Editors cannot be deep-linked (store-guarded): always enter through the day view.
- **API evidence**: capture the XHR responses of the named endpoints (base `/api/mobile/unified-time-recording/v1`, classic `/api/mobile/time-recording/v1`, legacy `/api/mobile/legacy-time-recording/v1`) and save them as `<name>.json` in the scenario's evidence folder. Every unified write returns the refetched `UnifiedDayPlan` of the day — save it too.
- **Oracle**: PEP's "Ist-Zeit Tag" per day (Phase 1 writes it to `results/<run>/pep-oracle.md`; after a write read it in PEP via `pep-verify`, lock the box first), the DB rows (`scripts/oracle-day.sh`), and the api-pp journal (oracles.md §1) when the service client is available. Values are compared as `H:mm`; keep raw ISO durations in notes. Which oracle applies to which number (root-caused 2026-10-15, details oracles.md §5):
  - **Unified credited** (day card, month row, month summary) = Σ `ZEITANRECHNUNG.ZEIT` with `AN_ZEITKONTO = 1` (GLAZ) per day = PEP "Ist-Zeit Tag" (identical on all first-run employees).
  - **Unified planned** (month column "Geplant") = Σ `PLANUNG.SOLLZEIT` of the day / month — never PEP "Soll" (= Arbeitsplan target TAGESSOLL × BG, a different value). The unified **day view shows no planned total** and its `time_amounts.planned` / balance come from the roster-cell planned layer: never assert them against the month row or PEP.
  - **Classic credited** (`/api/mobile/time-recording/v1`) = Σ stamp `creditedDuration` per shift + absence credits + unplanned/on-call (+ FLEX benefits); classic has **no Zeitsummen path**, so it is never compared with PEP Ist on a day with Zeitsummen.
  - **Legacy month** (`/legacy-time-recording/v1/reports/month`) = Σ stamp spans (corrected from/to) + on-call block spans for an employee with `time_stamp_add`, else Σ GLAZ `ZEITANRECHNUNG` for past days. A shift **without stamps** falls back to the span of its `planned_timestamps` (poma-core `ApiGatewayLegacyTimeRecordingService.getDurationsFromShift`, only up to today+1): 0:00 only when `planned_timestamps` is empty (first run); P2-painted days carry preview blocks that fill it (master-1822: E1's Zeitsummen-only Spät day 9:00, an un-stamped night 8:30), and auto-stamp days list their AS stamps there.
  - **Unified credited on a day without real blocks** (today, future, un-stamped plannings) = PEP's planned pre-credit (`ZEITANRECHNUNG` CODEART P) on a 1801 bundle; a pre-1801 bundle shows 0:00 (KD-7).
- **Known defects → KNOWN-FAIL**: a mismatch that matches (a) a row of "Known product defects" or (b) the scenario's entry for the bundle class under test in "Bundle-aware expectations" (both below) is reported as **KNOWN-FAIL** — worker verdict `FAIL`, `findings_confirmed: ["<id>"]` (KD-n, F-n, D-n or a listed N-id), `notes` and the dashboard verdict line start with `KNOWN-FAIL <id> <ticket>`, never in `new_findings`. The signature must match (the named numbers, status codes, error names); a FAIL with a different signature is new. A listed defect that does not show any more → normal PASS with "<id> not reproduced (fixed?)" in notes, so the orchestrator updates the status column.
- **Selectors** (no data-test attributes exist): unified shift card `pp-unified-shift-card`, stamp buttons `.unified-shift-card-stamp-btn` (past day) / `.unified-shift-card-stamp-multi-btn` (today), stamp row action buttons `button.unified-shift-card-ts-action-btn.edit|.delete` (aria-labels `ADD_EDIT.EDIT_TIME_STAMP` / `TIME_STAMP.TITLE`), add block `.unified-shift-card-add-block-wrapper ion-button`, on-call card `pp-unified-on-call-card` with `.unified-on-call-card-add-btn`, `.unified-on-call-card-stamp-btn`, `.unified-on-call-card-action-btn.edit|.delete`, day-level stamp control `.day-stamp-container`, day selector `.day-selector-arrow-btn` ×2 + `.day-selector-today-btn`, month report `.month-report-button`, table rows `.v1-month-report-container-table-row` (`.locked` + `.icon-lock`), footer `#primaryButton` (Save) / `#secondaryButton` (Cancel/Delete), header `#header-title`. Classic: card buttons `.stamp-time-block-btn`, `.extended-time-block-btn`, `.add-time-block-btn`, row icons `.edit-icon` / `.delete-icon`, add/edit route `add-edit/:type`.
- **Evidence naming**: `NN-<step>.png`, `<endpoint>.json`, `oracle-<what>.json`, `notes.md`.
- **Findings**: the F-ids a scenario confirms or refutes are listed; F-ids are defined in the report artifact (F1 attribution/shift-definition loss, F2 SHIFT_CONTROL enum, F3 classic NPE, F4 planned follows counted in BLOCKS mode, F5 preview-block duplication, F6 manual block deleted on replan, F7 rule-4 target time, F8 planned accounts from PLANUNG header, F9 flex balance, F10 new validation errors, F11 calendar-day split, F12 account id 0, F14 fixtures; D3 dangling allowance profile). Root causes and owners: the fix-plan facts (tables below).

Employees and prepared days are defined in data-plan.md (E1..E6, M-1 days D1..D7, M0 writable days −1..−5). On a DeployMate `customer-roster` seed they map to the realized days of `scripts/seed/README.md` § Dates (prepared P0..P3, write days WE1/WE2/WD1/WD2, today); the per-family executable steps are in `assets/family-briefs/<F>.md`. A line **"Data prerequisite / status on customer-roster seed"** under a heading says when a scenario cannot be evaluated on that seed (BLOCKED with that reason) and what would make it evaluable — since 2026-10-15 it names the Phase 1 step (`scripts/seed/README.md` steps j–r) that creates the data; BLOCKED only when that step was skipped or its verification failed.
